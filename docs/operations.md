# Operations

Asgard runs as a single-replica Deployment in the MicroK8s cluster on our VPS, alongside the other apps, at `https://asgard.joseforge.cz`.

## Build and deploy

- A multi-stage `Dockerfile` builds a static musl binary with the `dist` profile (LTO, stripped) and copies it onto `gcr.io/distroless/static-debian12`, built for `linux/amd64`. The image runs as uid/gid 10001, the VPS's default, has no shell, and owns `/data`, where `DATABASE_URL` points by default.
- The VPS defines every app with one values file rendered by a shared Helm chart. Asgard's is `deploy/asgard.yaml`; the operator deploys it into the namespace `asgard` with `./deploy.sh apply asgard`. The chart enforces a non-root user, a read-only root filesystem and no capabilities, and adds the Ingress with a Let's Encrypt certificate.
- The chart runs exactly one replica and stops the old pod before starting the new one (ADR 0004). Both probes check `/health/ready`. Only `/data` (the volume) and `/tmp` (for SQLite's temporary files) are writable.
- `deploy/asgard-secret.example.yaml` lists the Secret's keys only. The real Secret is sent to the operator encrypted (see [Secrets](#secrets)).

### Releases

Nobody tags or bumps the version by hand. `.github/workflows/release.yml` runs on every push to `master`:

1. Each squash-merged PR lands on `master` with its Conventional Commits title. Release Please opens or updates its release PR, which bumps `Cargo.toml` and `Cargo.lock` and adds the `CHANGELOG.md` entry. `feat:` bumps the minor version and `fix:` the patch. Before 1.0, a breaking change also bumps only the minor version.
2. Merging the release PR creates the `vX.Y.Z` tag and the GitHub Release.
3. The same workflow run then builds the image and pushes `ghcr.io/josefjura/asgard:X.Y.Z`. There is no `:latest`: the deploy tooling rejects it, and a tag is never overwritten. It can't be a separate `on: push: tags` workflow, because a tag pushed with `GITHUB_TOKEN` never triggers another workflow.

To deploy, set the new `X.Y.Z` in `deploy/asgard.yaml` (see [Upgrade](#upgrade)).

Things to know:

- The release PR is opened with `GITHUB_TOKEN`, so CI doesn't run on it. It only changes the version and changelog, and the commit it squashes from was already checked on `master`.
- The repository setting *Actions → General → Allow GitHub Actions to create and approve pull requests* must be on, or Release Please can't open its PR.
- If the image job fails, use *Re-run failed jobs* on that workflow run. It reuses Release Please's outputs from the first attempt, and the tag and Release stay in place. A fresh run wouldn't work, because Release Please reports a release only on the run that creates it.
- Configuration lives in `release-please-config.json` and `.release-please-manifest.json`. The manifest holds the last released version.

### Running the image locally

These flags match the restrictions the VPS enforces, so an image that runs this way runs there too:

```sh
docker build --platform linux/amd64 -t asgard .
docker run --rm --name asgard -p 8080:8080 \
  --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  -v asgard-data:/data \
  -e PUBLIC_URL=http://localhost:8080 \
  -e VAPID_PRIVATE_KEY=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAE \
  asgard
curl http://localhost:8080/health/live
curl http://localhost:8080/health/ready
docker stop asgard    # exits within a second or two: SIGTERM is handled
```

The placeholder VAPID key (the private key 1, which anyone can sign with) is only good enough to pass startup validation. The named volume `asgard-data` takes the image's ownership of `/data` on first use and keeps the database between runs; `docker volume rm asgard-data` starts over. To test a release against real data, mount a directory owned by 10001 that holds a copy of the production database instead (`-v "$PWD/testdata:/data"`).

### VAPID key

`VAPID_PRIVATE_KEY` is a raw P-256 private key, base64url without padding (43 characters). Generate one on any machine with OpenSSL:

```sh
openssl ecparam -genkey -name prime256v1 -noout \
  | openssl ec -outform DER 2>/dev/null \
  | tail -c +8 | head -c 32 \
  | base64 | tr '+/' '-_' | tr -d '=\n'
```

The DER encoding puts the 32-byte private key right after a 7-byte header, which is what `tail` and `head` cut out.

Generate it once and keep a copy in the password manager. Every push subscription is tied to this key: a new key silently stops notifications until each Member subscribes again.

### Secrets

Asgard's only secret is `VAPID_PRIVATE_KEY`, in the Secret `asgard-secret` under the key `vapid-private-key`. It can't be generated by the operator: it must be the key from the password manager, or every push subscription stops working. Encrypt it with [sops](https://github.com/getsops/sops) and the VPS's public age key, so only the server can decrypt it. Work outside the repository, so the plain value never lands in it:

```sh
cp deploy/asgard-secret.example.yaml ~/asgard-secret.yaml
# Paste the VAPID key between the quotes of vapid-private-key, then:
sops encrypt --in-place \
  --age age1gn5uyezusudmlcue7wtgfxnar6mntqfdp65ez5spveck42hghy5qaqctnc \
  --encrypted-regex '^(data|stringData)$' \
  ~/asgard-secret.yaml
grep ENC ~/asgard-secret.yaml    # the value must now look like ENC[AES256_GCM,...]
```

The encrypted file is safe to hand over. Secrets are read at startup, so changing one means restarting the pod.

### First deploy

The operator deploys from the VPS's own repository, with the values file and the encrypted Secret. The commands say `kubectl`; on the VPS it is `microk8s kubectl`, unless it is aliased.

1. **Check the prerequisites.**
   - The tag in `deploy/asgard.yaml` has been released: `ghcr.io/josefjura/asgard:X.Y.Z` exists.
   - `asgard.joseforge.cz` resolves to the VPS: `dig +short asgard.joseforge.cz`.
   - The encrypted Secret is ready (see [Secrets](#secrets)).
2. **Hand over** `deploy/asgard.yaml` and the encrypted `asgard-secret.yaml`. The operator creates the namespace `asgard`, loads the Secret and runs `./deploy.sh apply asgard`. Notes for the operator:
   - SQLite at `/data/asgard.db`, under 1 GB. Single instance only.
   - Migrations run on start, before the server listens.
   - The first Admin is created with a one-off `kubectl exec` (step 5).
3. **Watch the pod start.** If it crashes, the log names the missing or invalid variable:

   ```sh
   kubectl -n asgard rollout status deploy/asgard
   kubectl -n asgard logs deploy/asgard
   ```

4. **Check it from outside.** cert-manager requests the certificate when the Ingress appears, which takes a minute or two. This must print `ok` without `-k`, which proves the Let's Encrypt certificate is valid:

   ```sh
   curl https://asgard.joseforge.cz/health/ready
   ```

5. **Create the first Admin** as described in [The first Admin](#the-first-admin), and sign in.
6. **Check that data survives a restart.** Delete the pod, wait for the new one, and sign in again: the Admin and the passkey are still there.

   ```sh
   kubectl -n asgard delete pod -l app=asgard
   kubectl -n asgard rollout status deploy/asgard
   ```

### Upgrade

1. Merge the release PR and wait for the release workflow's image job to push `ghcr.io/josefjura/asgard:X.Y.Z`.
2. Test the new image against a copy of the production database (see [Running the image locally](#running-the-image-locally)). The old pod stops before the new one starts, so a release that fails to start means downtime.
3. Set `image.tag` in `deploy/asgard.yaml` to `X.Y.Z` and merge that change, so `master` always shows what is running.
4. Hand the new tag to the operator, together with any new variable or Secret key. New configuration must be in place before the image that needs it. The operator runs `./deploy.sh apply asgard`; then check:

   ```sh
   curl https://asgard.joseforge.cz/health/ready
   ```

Asgard is down for a few seconds while the old pod stops and the new one starts. Migrations run when the new pod starts.

**Rolling back:** set the previous tag and deploy again. That works only if the newer release added no migration: an older binary refuses to start on a database with a migration it doesn't know. In that case, restore the database from the last backup before the upgrade (see [Backups and restore](#backups-and-restore)) together with the older tag. Data entered since that backup is lost.

## Ingress and HTTPS

HTTPS is required for passkeys, Web Push and service workers. The chart renders Asgard's Ingress from `host` in `deploy/asgard.yaml`: ingress-nginx terminates TLS with a Let's Encrypt certificate from cert-manager, redirects HTTP to HTTPS, and passes plain HTTP to the pod. Asgard doesn't depend on the request's scheme: its cookies are always `Secure`, and its origin comes from `PUBLIC_URL`.

## Configuration

Environment variables, validated at startup. Secrets come from a Kubernetes Secret.

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | SQLite file on the volume |
| `PUBLIC_URL` | `https://asgard.joseforge.cz`; also the WebAuthn relying party, never change it (ADR 0005) |
| `VAPID_PRIVATE_KEY` | Web Push signing key |
| `HOST` / `PORT` | Listen address |
| `RUST_LOG` | Log filter |

## The first Admin

On a fresh database, create the first Admin's Invite link with the bootstrap subcommand. It runs with the same environment as the server, so in the cluster run it inside the pod:

```sh
kubectl -n asgard exec deploy/asgard -- /usr/local/bin/asgard bootstrap-admin "Josef"
```

It prints a link that works once, for 24 hours. Opening it registers a passkey and signs the new Member in as the Admin. The subcommand refuses once the Crew has an Admin; it is the only way to create one.

## Health

- `/health/live`: the process is up.
- `/health/ready`: the database answers. The chart uses it for both the liveness and readiness probes.

## Backups and restore

- Asgard takes no backups itself. The VPS backs up every `*.db` file on the app volumes nightly, encrypted and offsite, with `sqlite3 .backup`, which is consistent even in WAL mode. `/data/asgard.db` is covered with no setup on Asgard's side.
- Never copy the live file by hand; that can produce a corrupt backup.
- To restore, replace the database file on the volume with a backup and restart the pod.

## Heimdall import

A one-off subcommand that brings Heimdall's data into a fresh Asgard on the cutover day:

```sh
asgard import-heimdall <heimdall.db> --admin <display name>   [--rename <Heimdall name>=<display name>]... [--dry-run]
```

- **What it reads:** Heimdall's database, opened read-only, so a failed run can't damage it.
- **Members:** one per Heimdall user, named after its display name or its `--rename`. `--admin` names the Admin (after renames, ignoring case), so `bootstrap-admin` isn't needed. Every Member joins the Crew on the day of Heimdall's earliest entry, so every old Expense is split across all of them, as Heimdall split it. Discord ids are dropped.
- **Entries:** Expenses, Payments, Reminders and Quotes. Amounts become whole crowns. An Expense's date is the Prague day Heimdall recorded it. Imported entries have no Logger and imported Quotes no Added by. A Reminder still to come is pending; one already due is stored as sent, so nothing fires late on the first day. Heimdall never stored its todos.
- **Refusals:** it stops before writing anything if Asgard already has Members or entries, a Heimdall user is still an unassigned `emptyslot_*`, an entry refers to an unknown user, two Members would share a name, or `--admin` or a `--rename` matches nobody.
- **One transaction:** everything is written, then checked, then committed only if the checks pass. A dry run, or a failed check, rolls everything back.
- **Device links:** after a committed import it prints a Device link for every Member (one use, 24 hours). They are listed on the Admin page among the open links, where they can be revoked.

### Reading the report

The import prints four tables and a verdict:

- **Counts:** Expenses, Payments, Reminders and Quotes in Heimdall and in Asgard. They must be equal.
- **Totals (Kč):** what the Expenses and the Payments add up to, Heimdall's after each amount is rounded to whole crowns. They must be equal.
- **Balances (Kč):** each Member's Balance as Heimdall computes it (float Shares of each payer's summed Expenses, rounded to hundredths), Asgard's, and the difference. Each difference must be within 1 Kč.
- **Rounded to whole crowns:** every amount that wasn't whole crowns in Heimdall, with its original and rounded value. Usually `none`.

The last line is the verdict: `PASS. The import is committed.`, `PASS. Dry run, so nothing was committed.`, or `FAIL. Nothing was committed:` followed by each failed check. A failed check also makes the command exit with a non-zero status.

### Cutover

Heimdall runs from its repository's `docker-compose.yml` (container `heimdall`, database at `/app/data/heimdall.db`). Asgard must be deployed and empty: don't run `bootstrap-admin`. The `kubectl` commands are `microk8s kubectl` on the VPS.

1. **Tell the Crew** not to log anything in Heimdall for the day.
2. **Stop Heimdall**, so its database file is consistent. On Heimdall's host, from its repository:

   ```sh
   docker compose stop heimdall
   ```

3. **Copy Heimdall's database into Asgard's volume.** `docker cp` works on a stopped container. Fold any write-ahead log into the main file first, so the one file holds everything:

   ```sh
   docker cp heimdall:/app/data ./heimdall-data
   sqlite3 heimdall-data/heimdall.db 'PRAGMA wal_checkpoint(TRUNCATE);'
   ```

   Asgard's image has no shell or `tar`, so `kubectl cp` can't write into its pod. Copy the file through a short-lived pod that mounts the same volume instead:

   ```sh
   PVC=$(kubectl -n asgard get pvc -o jsonpath='{.items[0].metadata.name}')
   kubectl -n asgard run heimdall-copy --image=busybox --restart=Never --overrides='{
     "spec": {
       "securityContext": {"runAsUser": 10001, "runAsGroup": 10001},
       "containers": [{"name": "heimdall-copy", "image": "busybox", "command": ["sleep", "600"],
                       "volumeMounts": [{"name": "data", "mountPath": "/data"}]}],
       "volumes": [{"name": "data", "persistentVolumeClaim": {"claimName": "'"$PVC"'"}}]
     }}'
   kubectl -n asgard wait --for=condition=Ready pod/heimdall-copy
   kubectl -n asgard cp heimdall-data/heimdall.db heimdall-copy:/data/heimdall.db
   kubectl -n asgard delete pod heimdall-copy
   ```

4. **Rehearse with a dry run** and read the report (see [Reading the report](#reading-the-report)). Fix whatever it refuses, in Heimdall's copy or with `--rename`, and repeat until the verdict is `PASS`:

   ```sh
   kubectl -n asgard exec deploy/asgard -- /usr/local/bin/asgard import-heimdall      /data/heimdall.db --admin "Josef" --rename "josef_discord=Josef" --dry-run
   ```

5. **Run the real import:** the same command without `--dry-run`. Keep the output: it is the record of what Heimdall held.
6. **Send the Device links** over chat, each to its Member. Each one registers a passkey on the device that opens it.
7. **Check the Finance screen** against Heimdall's last known Balances, and against the report's Balances table.
8. **Leave Heimdall and its bot off.** Remove the copy from Asgard's volume (another `heimdall-copy` pod, `rm /data/heimdall.db`), keep `heimdall-data/` somewhere safe, and archive the Heimdall repository.
